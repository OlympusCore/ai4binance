# OOS Maturity Evidence Integration Reference

## ELI10

The maturity aggregator checks that the evidence belongs to the same research
candidate and that every required validation stage has usable proof. It does
not turn a research result into permission to trade.

## Authority and implementation

The validation obligations and promotion boundary come from sections 15 and 16
of `docs/governance/policy_organization_market_strategy_validation.md`.
The validation specification fields come from section 53 of
`docs/templates/reference_governed_validation_evidence_templates.md`.
This reference documents their implementation; it does not define thresholds,
change a governed policy or authorize an approval record.

`src/ai4binance/validation/oos_maturity.py` provides `OOSValidationSubject`,
`OOSArtifactReference`, `OOSMaturityEvidenceBundle` and `OOSMaturityGate`.
The subject composes `PromotionEvidenceQuery` with setup, feature-definition,
cost-model and validation-configuration hashes. Changing any identity field
changes its subject key; `as_of` controls freshness without changing identity.

## Artifact contract

Call `OOSMaturityGate(artifact_root).evaluate(bundle)` with relative,
SHA-256-bound references. The specification is itself an artifact whose digest
must equal the subject's validation-configuration hash. Its `scope` contains
the strategy ID, version, hash, symbol, market and timeframe in that order.
An active specification identifies its owner and supplies `requirements` by
stage. Each measurement rule has `operator` (`eq`, `in`, `gte`, `gt` or `lte`)
and `value`. Numerical thresholds are supplied by the governed specification,
not generated by the aggregator. An absent specification remains a blocker.

Stage artifacts carry `subject_key`, `stage`, `observed_at`, `expires_at`,
`blockers`, `measurements`, `source_artifacts` and `measurement_sources`.
Each measurement source identifies a zero-based source index and a JSON pointer
represented as a list of object keys or array indices. JSONL sources are read
as an array of events. The gate verifies the underlying bytes and measurement
equality instead of accepting a standalone summary. References are bounded to
the configured root and an 8 MiB read limit.

Each source also carries the same `subject_key`. A reference may specify an
`identity_pointer` for a nested or JSONL identity; the default is
`["subject_key"]`. Relabeling a wrapper cannot bind an older subject's source.
Every stage binds its underlying `blockers` measurement. Forward-paper sources
include `historical_oos_completed_at`, `observation_started_at` and
`observation_ended_at`; these dates must prove chronological forward observation.
Artifact expiry does not override the promotion registry's maximum evidence age.

The final-holdout artifact additionally binds chronological development,
walk-forward and holdout partitions, candidate freeze time, first access time
and an immutable holdout-access history. Prior access under a different subject
is contamination. Historical replay cannot substitute for forward-paper proof.
Spot and USD-M Futures subject identities and evidence chains remain separate.

## Runtime observations and review

`src/ai4binance/validation_pipeline_runtime.py` carries the configured
`BacktestConfig` through baseline, walk-forward and cost-stress evaluation.
Simulation assumptions and stress scenarios participate in checkpoint hashes.
Callers explicitly supply the simulation quantity in `BacktestConfig`; this
integration does not infer a position size or change the legacy default quantity.
Tuning supplies the complete searched hypothesis count to statistical
assessment; Bonferroni correction affects the confidence interval used by the
existing evidence gate.

The immutable historical decision cache allocates dataset slots only when a
playbook first enters the cache. Cache hits retain object identity without a
discarded dataset-sized allocation; this changes no simulation calculation.

Historical validation writes a content-addressed `*.oos-maturity.json`
observation beside its existing evidence. `UNBOUND_EXPLORATORY_EVIDENCE` means
the underlying reports exist but do not yet form an exact maturity packet.
This observation lists the actual artifacts and retains their blockers.
It must not be relabeled as an untouched final holdout or as paper-forward data.

The independently reviewed promotion artifact references
`oos-bundle:sha256:<bundle digest>` through the existing promotion registry.
Identity, expiry, conflict and revocation checks remain applicable.
`OOS_MATURITY_COMPLETE` means only that this packet meets its evidence checks.
All outcomes retain `execution_allowed=false`, `RESEARCH_ONLY` and
`LIVE_ORDER_BLOCKED`; consequential authority remains outside this aggregator.

## Verification

Run the focused OOS maturity, validation pipeline, walk-forward, tuning,
Futures OOS and promotion evidence tests, followed by the canonical FULL gate.
Tests cover missing stages, stale/conflicting evidence, changed parameters,
artifact tampering, path escape, holdout contamination, summary-only promotion,
cost configuration propagation and multiple-testing correction.
